# GPU Failure Operations: source notes

Reviewed manually September 22, 2026. The article's incident, memory values, policy threshold, shortened IDs, and downloadable receipts are synthetic. These notes replace the generated packet. Relevant documentation selections were read, not entire upstream APIs or projects.

## Sources inspected

- [PyTorch memory snapshots](https://docs.pytorch.org/docs/main/torch_cuda_memory): allocator visibility, direct-CUDA/NCCL blind spots, device_memory_used, local-only memory_viz, OOM event history, private snapshot APIs, finite ring-buffer behavior, and maximum-entry guidance. Enable history before the window; a late or overwritten history can miss a real OOM. No GPU instrumentation was executed.
- [PyTorch 2.14 CUDA semantics](https://docs.pytorch.org/docs/2.14/notes/cuda.html): caching versus allocated memory, native and cudaMallocAsync backends, max_split_size_mb as a last resort, ignored native tuning under async allocation, and backend-specific statistics. The stable URL currently serves a client-side redirect to 2.14; the shared reference now links directly to the inspected version. The main-doc backend-specific-statistics note was also checked at https://docs.pytorch.org/docs/main/notes/cuda.html.
- [NVML overview](https://docs.nvidia.com/deploy/nvml-api/nvml-api-reference.html), [device queries](https://docs.nvidia.com/deploy/nvml-api/api/group__nvmlDeviceQueries.html), [memory-info v2 struct](https://docs.nvidia.com/deploy/nvml-api/api/structnvmlMemory__v2__t.html), and [clock-event reasons](https://docs.nvidia.com/deploy/nvml-api/api/group__nvmlClocksEventReasons.html): query capabilities, memory-info v1/v2, MIG scope, operating-system framebuffer accounting, and expected versus unexpected clock limits. NVML system reservation and PyTorch allocator reservation aren't the same field. Retained framebuffer pages don't prove a stale process. Power-cap events can be expected under an approved limit.
- [NVIDIA Xid introduction](https://docs.nvidia.com/deploy/xid-errors/introduction.html): events can arise from hardware, NVIDIA software, or user applications; codes guide investigation rather than prove a physical defect.
- [Current Xid catalog](https://docs.nvidia.com/deploy/xid-errors/analyzing-xid-catalog.html): exact Xid 94/95 entries and recovery actions. Xid 94 requires affected-application restart; peers remain unaffected and reset is recommended when convenient. Xid 95 requires GPU reset before applications restart. The generated packet's idle-memory/workload-survival explanation was wrong.
- [GPU Operator troubleshooting](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/troubleshooting.html): kernel Xid capture and device-plugin health reporting. The article's 26.3 reference is version-qualified; no claim that every Xid causes an identical plugin action was added.
- [Kubernetes device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/): unhealthy devices reduce allocatable count, while existing pod assignments persist. Health reporting doesn't supply eviction or application-readiness control.
- [CUDA asynchronous execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html): errors can surface at synchronization, cudaGetLastError clears the record, and CUDA_LAUNCH_BLOCKING changes execution and can slow it. A successful later error query doesn't undo the first failure.
- [CUDA Runtime 13.4 error enums](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__TYPES.html): illegal address, launch timeout, assert, hardware stack, illegal instruction, misaligned address, invalid address space/PC, launch failure, tensor-memory leak, MPS-client termination, and contained-error recovery selections. Listed process-invalidating errors require termination/relaunch. Added the inspected contained label to the worksheet. Its set remains illustrative; unknown codes hold admission for exact semantic resolution.
- [GPU Operator driver upgrades](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-driver-upgrades.html): explicit cordon/eviction/drain/validation stages, separate force and emptyDir flags, and workload disruption. Deleting emptyDir data isn't a blanket force-eviction option. A node drain can disrupt unrelated workloads.
- [DCGM diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html): current four-level test table and stated non-goals. Level 1 runs software checks; Level 2 adds PCIe/NVLink and memory coverage; nvbandwidth/NCCL begin at Level 3. Diagnostics don't repair hardware or replace comprehensive field diagnosis/RMA procedures.
- [DCGM plugin reference](https://docs.nvidia.com/datacenter/dcgm/latest/reference/diagnostics/plugins/index.html): actual plugin purposes and distinction between transport, framebuffer, power/stress, and single-node collective coverage. Plugin availability and result details matter. Skip/Not Run aren't Pass.

## Corrections and teaching decisions

The original visible article already made most operational distinctions correctly. Its broad memory accounting needed the NVML version/NUMA caveat. Added exact Xid 94/95 recovery and error-record clearing because both address misleading intuitions without turning the lesson into a command cookbook. Replaced one generic ownership question with the catalog distinction; retained nine questions.

The original read-only analyzer misclassified the original memory layout as fragmentation when cuda_error was success. It also returned unclassified for a captured OOM with zero request size. Both were reproduced by direct CPU execution. OOM-specific arithmetic now requires an actual captured OOM and positive size; missing size can be null and yields oom-unresolved. A worked comparison holds memory readings constant while varying event evidence. A successful operation's status mustn't be substituted for an earlier failed operation.

Malformed backend lists raised TypeError, and an oversized integer raised OverflowError instead of the worksheet's declared ValueError. The input guards now reject those cases, empty receipt identity, and boolean numeric values. Accounting comparisons retain the documented rounding tolerance. The existing eight-record output and independent relaunch gate remain intact; mixed Xid 94/contained error is also checked.

Removed unsupported generated assertions that kernel logs are the sole truth, every page-retirement count shares a universal 64-page replacement threshold, reset failure automatically mandates physical replacement, readmission requires a universal 12–24-hour maximum-utilization run, and zero clock limiting is always a success criterion. No such universal prescriptions follow from the inspected sources. Counter interpretation, reset capability, test coverage, load, and duration need architecture/version/incident-specific policy.

The generated injection command and automatic-controller promises weren't independently substantiated and weren't promoted into the article. These exercises manipulate local normalized receipts; they don't inject device failures, validate monitoring integration, authenticate events, authorize reset, or implement a durable cluster quarantine state.
