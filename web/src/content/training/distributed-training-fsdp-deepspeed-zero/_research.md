# Manual research review: distributed training

Checked September 22, 2026. These notes replace a generated packet with malformed equations, an unsupported FSDP2 memory benchmark, a specific deprecation-version assertion without primary evidence, and universal networking/performance promises.

## Memory and numerical assumptions

- The ZeRO paper's mixed-precision Adam inventory is one recipe: 2-byte parameters, 2-byte gradients, 4-byte master parameters, and two 4-byte moments. Its ideal model-state formulas are `16P` for replication, `4P + 12P/N` for stage 1, `2P + 14P/N` for stage 2, and `16P/N` for stage 3. These exclude gathered units, transient gradients, activations, and runtime buffers. N is the sharding group size. https://arxiv.org/html/1910.02054v3
- A 70B model therefore has 1,120 decimal GB under that recipe. A BF16 replica's 140 GB of parameters already exceeds the example's 80 GB capacity. Ordinary PyTorch AdamW allocates moments lazily at an update; don't describe the entire inventory as allocated before the first forward. AdamW inherits the Adam implementation, whose _init_group creates the moments. https://github.com/pytorch/pytorch/blob/v2.14.0/torch/optim/adamw.py and https://github.com/pytorch/pytorch/blob/v2.14.0/torch/optim/adam.py
- Adam's squared-gradient average is an uncentered second moment, not a centered variance. FP32 stored weights reduce rounding loss but cannot preserve every decrement. At exactly 1.0, the downward gaps are `2^-11` for FP16, `2^-8` for BF16, and `2^-24` for FP32. The article's CPU nextafter/subtraction experiment checks them and shows that subtracting `1e-8` disappears even in FP32. Spacing and representable range are different questions. https://docs.pytorch.org/docs/stable/generated/torch.nextafter.html

## Collectives and FSDP2 lifecycle

- For equal chunks, ring bytes sent per rank are `(N-1)/N * S` for reduce-scatter or all-gather and twice that for all-reduce. S is the full reduction input or full gathered output, not a local all-gather shard. Sum examples don't imply every reduction is sum or that DDP omits its averaging division. https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html
- NCCL selects available algorithms based on topology and architecture by default; ring formulas are a model, not a wire trace of every collective. https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html#nccl-algo
- ZeRO section 7.2 derives two collective phases for optimizer-plus-gradient partitioning and three for full partitioning, under equal communication dtypes. A full gradient all-reduce plus parameter all-gather is three phases, not the same two-phase accounting. Stage-1 storage policy alone doesn't fix the collective schedule. https://arxiv.org/html/1910.02054v3
- Current DeepSpeed stage-1/2 code has bucketed reduction paths controlled by `reduce_scatter`, including all-reduce paths. Thus storage-stage labels aren't an exact communication trace. Pinned source inspected September 22. https://github.com/deepspeedai/DeepSpeed/blob/2a4ee92b76601ef2709c4e9857eab4e232f72075/deepspeed/runtime/zero/stage_1_and_2.py
- FSDP2 gathers unit parameters and computes local **unsharded gradients** before reduce-scatter. The persistent shard inventory doesn't remove that temporary gradient storage. Stored parameter dtype, gathered compute dtype, and reduction dtype can differ. https://docs.pytorch.org/docs/2.14/distributed.fsdp.fully_shard.html
- The current root default retains gathered parameters after forward; non-root units reshard. An explicit True overrides that choice. An integer proper divisor enables partial resharding with more retained parameter memory and smaller backward gather groups. https://docs.pytorch.org/docs/2.14/distributed.fsdp.fully_shard.html
- The official tutorial marks FSDP1 deprecated and teaches bottom-up fully_shard plus optimizer construction after sharding. It also explains implicit prefetch, explicit prefetch's memory cost, DTensor clipping, and FP32 shards without an additional FP32 master. No universal speedup or percentage memory reduction is established here. https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html
- FSDP1 CPUOffload(offload_params=True) also offloads gradients and puts optimizer updates on CPU; FSDP2 CPUOffloadPolicy includes parameters, gradients, and optimizer state. Neither is a built-in NVMe policy. https://docs.pytorch.org/docs/2.14/fsdp.html#torch.distributed.fsdp.CPUOffload and https://docs.pytorch.org/docs/2.14/distributed.fsdp.fully_shard.html#torch.distributed.fsdp.CPUOffloadPolicy
- Gradient clipping's global norm can communicate even though ordinary shard-local AdamW updates need no new parameter collective. optimizer.step doesn't clear gradients. Releasing unsharded tensors also doesn't force the CUDA allocator to return reserved memory. https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html#gradient-clipping-and-optimizer-with-dtensor and https://docs.pytorch.org/docs/stable/notes/cuda.html#memory-management

## Networking and parallel axes

- Hardware specifications are SKU-specific. HGX H100 SXM lists 900 GB/s NVLink bandwidth; B200 lists 1,800 GB/s. HBM bandwidth is separately 3.35 TB/s and up to 8 TB/s. NIC count and GPU-host PCIe topology matter. https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory-h100-h200-b200/latest/components.html
- The 900 GB/s H100 NVLink figure is aggregate bidirectional bandwidth. NVIDIA also explicitly describes B200's 1.8 TB/s/GPU interconnect as bidirectional. Avoid comparing these with one-way NIC rates to claim a universal slowdown factor. The H100 post's slug currently redirects to a different article; its post-ID URL returns the intended source. https://developer.nvidia.com/blog/?p=53977 and https://developer.nvidia.com/blog/how-to-scale-fast-fourier-transforms-to-exascale-on-modern-nvidia-gpu-architectures/
- GB200 NVL72 joins 72 GPUs into a rack-scale NVLink domain; node count and fast-domain size aren't interchangeable. https://docs.nvidia.com/multi-node-nvlink-systems/multi-node-tuning-guide/overview.html
- ConnectX-7/8 offer 400/800 Gb/s interface specifications. Dividing by eight gives theoretical 50/100 GB/s line rates per direction, not usable per-GPU collective throughput. https://www.nvidia.com/en-au/networking/infiniband-adapters/
- GPUDirect RDMA is direct exchange with a supported peer device such as a NIC, subject to platform and driver requirements. It differs from GPU peer access across NVLink. https://docs.nvidia.com/cuda/gpudirect-rdma/
- Classic Megatron TP uses paired column/row linear partitions, with two forward and two backward all-reduces per transformer layer under its replicated layouts. Other layouts can change those collectives. TP's communication cost doesn't create a correctness ban against crossing nodes. https://arxiv.org/html/2104.04473v5
- For a regular mesh, world size is DP*TP*PP*CP. With DP defined as independent sequence replicas, the global sequence batch is microbatch_sequences * accumulated_microbatches * DP. CP divides one sequence's tokens rather than adding independent samples. The paper gives the DP/TP/PP batch relationship; the article explicitly extends its counting convention to CP. https://arxiv.org/html/2104.04473v5
- The 2019 PipeDream paper names the 1F1B schedule. Its asynchronous weight stashing differs from synchronous flush schedules. Relevant historical sections checked in the paper text. https://aaronharlap.github.io/papers/sosp19-pipedream.pdf
- For balanced non-interleaved flush schedules, GPipe and plain 1F1B have the same ideal bubble time. `(p-1)/m` is overhead relative to useful compute; `(p-1)/(m+p-1)` is idle fraction of elapsed time. Plain 1F1B reduces retained activation sets. Interleaving reduces the ideal bubble at the cost of extra boundary transfers. https://arxiv.org/html/2104.04473v5
- Pinned Megatron code uses warmup `min(m, p-i-1)` for the classic non-interleaved path, alternates forward/backward, and removes completed saved entries. The maximum outstanding count includes the following steady-state forward. https://github.com/NVIDIA/Megatron-LM/blob/c711dc0a7f4f7460045cae18ec2f9ff5f4b92b5e/megatron/core/pipeline_parallel/schedules.py
- Ring Attention conditions transfer hiding on block compute taking long enough. It uses online softmax statistics; its original JAX code exchanges KV with lax.ppermute. The paper evaluates 32 A100s connected by InfiniBand, directly contradicting an intra-node-only rule. Longer feasible context isn't a universal zero-cost guarantee. https://arxiv.org/html/2310.01889v4

## DeepSpeed and resume boundaries

- Current configuration docs support AutoTP with ZeRO stages 0-3. PipelineModule still excludes stages 2/3. Older tutorials/releases can differ; pin and test the installed stack. https://www.deepspeed.ai/docs/config-json/#tensor-parallel-autotp and https://deepspeed.readthedocs.io/en/latest/pipeline.html
- The shown default CPU optimizer-offload path selects DeepSpeedCPUAdam, with AdamW mode for AdamW config. torch_adam and ZenFlow choose other paths; this isn't a universal optimizer-class assertion. https://github.com/deepspeedai/DeepSpeed/blob/2a4ee92b76601ef2709c4e9857eab4e232f72075/deepspeed/runtime/engine.py
- Dynamic ZeRO-3 routing can diverge in parameter-gather order. Leaf modules cause gathering of descendant parameters before entering the dynamic region. https://deepspeed.readthedocs.io/en/latest/training.html#zero-leaf-modules
- Universal Checkpointing requires ordinary save, explicit conversion, and load_universal; it isn't arbitrary architecture conversion. Changes in grouping/reduction order also affect continuation even when reshaping succeeds. https://www.deepspeed.ai/tutorials/universal-checkpointing/

## Teaching and validation boundaries

The lesson follows bytes from replica storage to sharded state, transient unit materialization, network transfers, topology, and resume. CPU examples distinguish arithmetic or local mechanism checks from actual distributed execution. The rounding and pipeline counterexamples prevent two superficially plausible explanations from surviving an executable check.

Native illustrations show assumptions and corrected gradients/collective counts. Hardware figures are specifications; the 18 GB extra-memory sizing assumption is authored. No 70B model, multi-GPU NCCL job, offload benchmark, or distributed checkpoint restore is run for this review. Real fit, throughput, convergence, and fault recovery still require the intended workload.
