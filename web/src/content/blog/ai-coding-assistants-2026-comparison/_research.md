You can still write every line yourself. A workflow to evaluate is to describe the task, give the assistant the repository rules, let it patch and test, then review the diff. Agent surfaces can assemble context, plan, edit files, run tests and return reviewable changes; those capabilities don't establish that they outperform manual work on every task.

## The Agentic Loop

Start with the authorization task. A weak prompt says, "add admin settings auth." A useful brief names constraints: use the existing JWT middleware in `app/middleware/`, read `db/schema.ts`, require active workspace admin membership, reject expired permissions, keep hashing on Argon2id, and add targeted tests.

Once the assistant has a clear brief, it moves through a strict delivery loop:

### 1. Assemble Context: Search and rules

Before writing code, the assistant searches for the smallest file set that can answer the task. This includes your schema, middleware conventions, `package.json`, and project instructions like Claude's `CLAUDE.md` or Cursor's `.cursor/rules`. It narrows the repository down to a working set.

### 2. Plan and Patch: Propose and edit

The agent proposes a plan: reuse the existing JWT helper, query the workspace membership, check expiration dates, and wire the route. Once approved, the agent edits multiple files in coordination.

### 3. Test and Repair: The evaluator-optimizer loop

If the first test run fails (e.g., expecting a 403 but getting a 200), a line-completion tool stops. An agent reads the failure, reopens the middleware, fixes the date comparison logic, and reruns the tests. Agents turn test failures into narrower next steps.

### 4. Human Review: Enforcing policy

The diff turns green, but you still review it. If the assistant imported `bcrypt` out of habit when your brief required `Argon2id`, you reject that hunk. Passing tests don't prove policy compliance. You restate the requirement and force the agent to fix the dependency.

That is the contract: the assistant handles routine search, patching, and test iteration, while the human owns architecture, security posture, dependency choices, and release judgment.

## Designing a Reliable Workflow

A reliable workflow matters more than a flashy launch demo. Before buying into any of these tools at a team level, evaluate them against these core checks:

- **Environment ownership:** Does work happen in local files, an isolated worktree, GitHub Actions, or a remote sandbox?
- **Context assembly:** Does the tool reliably find the right files without dragging the whole repository into the context window?
- **Test loop:** Can it run the right tests, read failures, and retry without hiding red builds?
- **Data policy:** Which plan protects code and prompts from model training by default?

## Common Beginner Mistakes

When starting with agentic workflows, avoid these common traps:

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Vague first prompt | The agent creates a parallel accounts table even though your app already has users . | Make the first prompt a task brief: define files to inspect, constraints to preserve, and behavior to reject. |
| Passing tests but wrong architecture | The code passes targeted tests but duplicates validation logic or ignores repo style. | Reject oversized diffs. Ask for smaller patches and keep linting rules highly visible to the agent. |
| Security blindness | The agent hardcodes a token, picks a stale dependency, or writes permissive access checks. | State security constraints up front. Add negative tests and manually review dependencies and secrets. |

## How to Evaluate Effectively

Don't compare tools using a single toy prompt. Build a small evaluation set and rerun it when vendors change models or pricing structures. Benchmarks like SWE-bench provide a useful baseline because they ask models to resolve real GitHub issues against test suites, but your own repository tasks are what actually dictate your purchase decision.

Use a five-task evaluation pack on each candidate tool:

| Task Type | What it Reveals | Good Signal |
| --- | --- | --- |
| Small bug fix | Local search and patch size | Targeted test passes with minimal code churn. |
| Multi-file refactor | Planning and dependency tracking | Public API stays stable and tests update correctly. |
| Failing test repair | Failure inspection capabilities | Tool uses the actual error output instead of guessing. |
| Security-sensitive change | Policy awareness | Unsafe actions are refused, escalated, or automatically corrected. |
| Docs update | Context consistency | Documentation matches the code and avoids stale claims. |

Score the entire loop: how many clarifications were needed, diff size, risky-command approval, and review speed, not just the final code text.
