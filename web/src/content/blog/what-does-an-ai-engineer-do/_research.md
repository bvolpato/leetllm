# Page Structure: What Does an AI Engineer Actually Do?

## 1. Introduction: The New Engineering Limit

**Goal:** Define applied AI engineering by a tested model-backed workflow. Broader AI and research engineering titles may instead own training infrastructure or experiments; inspect the posting rather than imposing one universal limit. Examples checked September 23, 2026: [OpenAI Applied AI Engineer](https://openai.com/careers/applied-ai-engineer-digital-natives-san-francisco/), [Anthropic RL Engineering](https://job-boards.greenhouse.io/anthropic/jobs/4952051008), and [Anthropic ML Reinforcement Learning](https://job-boards.greenhouse.io/anthropic/jobs/4613568008).

- **Content to include:**

- Define the fundamental shift: moving from delivering custom ML models to operating a measured software loop around a foundation model (retrieval, tools, responses, evaluations).
- Credit the popularization of the term to [Swyx's 2023 essay, "The Rise of the AI Engineer"](https://www.latent.space/p/ai-engineer).
- **Visual Concept (to describe in text):** A flowchart showing the product loop. A user need dictates a prompt spec, which pulls in evidence/tools, makes a model call, and undergoes validation/evals before returning to the user.
- **Comparison Table: Role Differences**

- **Data Science:** Focuses on analysis and decision support ("Does the evidence support this decision?").
- **ML Engineering:** Focuses on training models and production ML pipelines ("Can this model train, deploy, and stay reliable?").
- **AI Engineering:** Focuses on model-backed product workflows ("Can this feature use models safely, cheaply, and measurably?").

## 2. The Six Pillars of AI Engineering

**Goal:** Break down the day-to-day technical ownership of the role. Avoid vague concepts; use concrete engineering terminology.

- **Prompt Specs and Structured Output:**

- Explain that prompting is a software spec, not "asking nicely."
- Highlight the necessity of typed fields over unstructured text (e.g., using schemas to extract `account_status` and `next_action`).
- **Reference:** Detail how major providers enforce this, such as the [OpenAI Structured Outputs API](https://platform.openai.com/docs/guides/structured-outputs).
- **RAG and Retrieval Systems:**

- Contrast "demo RAG" (a folder of PDFs and a vector database) with "production RAG" (parsing, chunking, exact-match search, reranking, and strict permission filtering).
- Choose retrieval from observed failures. BM25 ranks lexical term matches; it isn't a guaranteed exact-ID lookup, and hybrid retrieval isn't mandatory. Use a keyed lookup for known identifiers, then test dense, lexical, or hybrid retrieval for the document task. Sources: [BM25 and Beyond](https://doi.org/10.1561/1500000019) and [Dense Passage Retrieval](https://arxiv.org/abs/2004.04906).
- **Reference:** For foundational context on dense retrieval, cite the original [Dense Passage Retrieval (DPR) paper](https://arxiv.org/abs/2004.04906).
- **Agents and Tool Control:**

- Define agents as model-driven loops that call tools (APIs, DB lookups). The hard part is control, authorization, and stopping rules.
- ReAct interleaves reasoning and actions so observations can update the plan; it doesn't require a fixed upfront action sequence. Avoid claiming that every plan-and-execute implementation is irrevocable or inherently better for a task. The [ReAct paper](https://arxiv.org/abs/2210.03629) supports the interleaving mechanism, not a universal comparison with other architectures.
- **Reference:** Cite the [ReAct framework paper by Yao et al.](https://arxiv.org/abs/2210.03629) and the standardization of tool exposure via the [Model Context Protocol (MCP)](https://modelcontextprotocol.io/).
- **Inference, Serving, and Cost Management:**

- Explain the configured provider's actual billing categories rather than assuming every endpoint has input, cached-input, and output rates. This article needs no volatile price example.
- Discuss the technical bottleneck of the KV cache (attention state for previous tokens).
- **Reference:** Point to standard serving stacks like [vLLM](https://github.com/vllm-project/vllm) and the [PagedAttention mechanism](https://arxiv.org/abs/2309.06180) that optimizes KV cache memory.
- **Lightweight Adaptation:**

- Explain the decision tree for adaptation: try RAG for fresh facts, structured output for format issues, and tuning only for durable behavioral/style changes.
- **Reference:** Highlight techniques like [Low-Rank Adaptation (LoRA)](https://arxiv.org/abs/2106.09685) over full model pretraining.
- **Evaluation and Regression Testing:**

- Identify this as the biggest difference between demos and production.
- Use versioned product cases and regression gates. Direct assertions suffice for many exact rules; human review or a calibrated model judge may be needed for semantic faithfulness. A model judge isn't compulsory, and citation presence alone doesn't prove support.
- **Reference:** Contrast internal product evals with generalized public benchmarks like [SWE-bench](https://www.swebench.com/) or [MMLU](https://arxiv.org/abs/2009.03300).

## 3. A Week in the Life: Ownership Examples

## 4. Practical Takeaway: Diagnosing a Bad Output

**Goal:** Provide an actionable checklist for debugging a model workflow.

- **Step-by-Step Trace:**

1. Check user identity and document access scope.
2. Inspect retrieved document IDs and their reranked scores.
3. Compare the final context packet against generated claims.
4. Verify schema validation and frontend rendering.
- **Debugging limit:** A prompt can't supply missing external source evidence. It may still improve abstention or request another authorized lookup. Add the reproduced failure to the relevant regression set and contain active incidents before waiting for a complete repair.

## 5. How to Break In & Portfolio Standards

**Goal:** Provide career transition advice for adjacent roles and set a high bar for portfolio projects.

- **For Software Engineers:** You have the systems knowledge. Learn transformer fundamentals, retrieval evals, inference economics, and how to build a tool-using agent with strict stopping rules.
- **For Data Scientists:** You have the measurement skills (experimentation, evaluation). Close the gap by building typed backend APIs and studying deployment observability.
- **Portfolio Acceptance Criteria:**

- *Behavior:* A written spec of supported inputs/outputs and an eval set with edge cases.
- *Safety:* Retrieval access checks, tool idempotency, and risk simulation.
- *Operations:* Distributed tracing, token-use dashboards, and a rollback plan.
- *Reproducibility:* Pinned dependencies and saved eval outputs.
