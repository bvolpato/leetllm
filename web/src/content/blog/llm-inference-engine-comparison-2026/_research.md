## What Engines Compete Over

When a large language model generates text, it predicts one token at a time. To predict token 10, it needs information from tokens 1 through 9. Recomputing that history at every step would waste most GPU work, so serving systems store intermediate attention state in a **KV cache**.

Inference usually has two phases:

- **Prefill:** Processes the prompt and writes the first KV-cache entries.
- **Decode:** Loops one output token at a time while reading that cached state.

These phases surface in user latency as **TTFT** (Time To First Token, including network and queueing) and **TPOT** (Time Per Output Token after the first). KV memory can limit admission. A fixed worst-case reservation can trap unused capacity; modern allocators, schedulers, kernels, and parallelism must be considered together.

### Why PagedAttention Matters

vLLM's original breakthrough was **PagedAttention**. It attacks KV-cache fragmentation by allocating cache in fixed-size blocks instead of one large contiguous segment per request.

Let's look at the allocation arithmetic:

- A GPU has 24 GB of VRAM.
- Model weights consume 18 GB, leaving 6 GB for KV cache and active requests.
- If contiguous reservation takes 1 GB per request slot, you get six slots.
- If most requests use only 400 MB, 600 MB per slot sits empty.

PagedAttention breaks the cache into blocks. A 400 MB request gets roughly 400 MB of blocks, so the same 6 GB budget can hold about fifteen average requests instead of six worst-case reservations. More memory headroom means the scheduler can keep more sequences active instead of leaving GPU capacity idle.

## Engine Choices in 2026

### vLLM: Broad Production Default

vLLM is the balanced starting point for many production teams. It offers broad model coverage, OpenAI-compatible serving patterns, a large user base, and PagedAttention as its core memory-management idea.

Official [vLLM GPU installation docs](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/) cover NVIDIA, AMD, Intel XPU, and Apple Silicon through a hardware plugin; TPU and Gaudi have their own plugin docs. Modern vLLM has [automatic prefix caching](https://docs.vllm.ai/en/stable/design/prefix_caching/), including cache-salt isolation. Prefix caching skips matching prefill work, not decoding a new response.

### SGLang: Prefix-Reuse Specialist

SGLang introduced **RadixAttention** specifically optimized for KV-cache reuse across shared token prefixes. This design is highly relevant when requests repeat large prompt regions:

- Multi-turn chat with a long system prompt
- Retrieval-Augmented Generation (RAG) over repeated context
- Few-shot prompts with shared exemplars
- Agent loops that revisit similar state

A common system prompt creates an opportunity for reuse; it doesn't prove SGLang beats vLLM with caching enabled. Verify exact tokens, routing locality, cache isolation, eviction, and hit rate. The original [SGLang paper](https://arxiv.org/abs/2312.07104) explains RadixAttention; [current documentation](https://docs.sglang.io/) also covers distributed serving and broad hardware support.

### TensorRT-LLM: NVIDIA Throughput Path

TensorRT-LLM targets NVIDIA hardware with optimized kernels, caching, quantization, and distributed serving. No universal throughput lead or H100 percentage advantage is established here. Check the version-specific model and feature matrix and run equivalent workloads.

Continuous batching admits new work without waiting for an entire static batch to finish. The rolling [TensorRT backend removal guide](https://nvidia.github.io/TensorRT-LLM/legacy/tensorrt-backend-removal.html), updated September 14, says PyTorch is the sole execution backend and `trtllm-build` is removed. Don't infer behavior of stable v1.2.1 from an unversioned migration page or repeat a universal compilation tax.

### Ollama: Local-Development Runtime

Ollama prioritizes local predictability over datacenter benchmarks. It provides a local daemon, simple CLI flows, and a clean API that supports OpenAI-compatible local endpoints for seamless client code testing.

Ollama can [import GGUF](https://docs.ollama.com/import), a tensor-and-metadata format used by llama.cpp. The March 30 [MLX preview announcement](https://ollama.com/blog/mlx) describes a separate Apple Silicon execution path. Verify the installed version and selected model backend instead of assuming every Ollama model uses GGUF or llama.cpp.

## Current Frontier Model Compatibility

Leading 2026 open-weight checkpoints require exact runtime compatibility:

- **[GLM-5.2](https://unsloth.ai/docs/models/glm-5.2):** A 744B-A40B Mixture-of-Experts (MoE) with 1M context. It natively documents vLLM and SGLang support.
- **[DeepSeek V4 Flash 0731](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731):** Features a 284B/13B core with an attached DSpark speculative module. Official release recipes specifically target vLLM and SGLang.

Generic Transformers support doesn't guarantee that an exact checkpoint's quantization, sparse kernels, or speculative decoding will work. Always start with the vendor's officially recommended runtime recipe.

## How to Choose

Benchmark tables are only useful if they change a deployment decision. Start with vLLM for server deployments and Ollama for local iteration. Specialize only when measurements demand it.

Before replacing a serving runtime, evaluate a benchmark that genuinely mimics your production traffic. Track prompt length, output length, shared-prefix hit rate, burst shape, and hardware target.

Avoid these three common mistakes:

1. Applying a legacy compiled TensorRT-LLM recipe to a release whose execution backend has changed.
2. Treating aggregate tokens per second as synonymous with user latency.
3. Trusting one benchmark shape as universal truth. Benchmark both unique-prompt and shared-prefix workloads before migrating.
