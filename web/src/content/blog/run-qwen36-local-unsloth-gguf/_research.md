# Run Qwen3.6 Locally with Unsloth GGUF

Setting up a private coding assistant on your workstation requires balancing memory, speed, and model capability. Qwen3.6, combined with `llama.cpp` and Unsloth GGUF files, provides a practical local setup for repository-level reasoning without exposing your source code to hosted APIs.

The official repository notes that Qwen3.6 focuses on stability, agentic coding, repository-level reasoning, and thinking preservation ([Qwen3.6 GitHub](https://github.com/QwenLM/Qwen3.6)). While Ollama offers direct `qwen3.6:27b` and `qwen3.6:35b` tags for rapid deployment ([Ollama Qwen3.6 Model Library](https://ollama.com/library/qwen3.6)), the Unsloth GGUF path via `llama.cpp` keeps exact file versions, quantization tiers, and Multi-Token Prediction (MTP) variables completely visible for deliberate tuning.

## Pick the Right First Model

For local deployment, two open-weight Qwen3.6 models are the primary targets. Start by optimizing for a clean debug loop, changing one variable at a time before testing more complex paths.

- **Qwen3.6-27B (Dense):** A standard dense architecture where every parameter computes for every token. Best for a 16 GB planning target and keeping runtime variables simple.
- **Qwen3.6-35B-A3B (MoE):** A Mixture-of-Experts model. According to its release data, it features 35B total parameters but only activates 3B per token using 256 experts (8 routed + 1 shared active during inference) ([Unsloth Qwen3.6-35B-A3B Hugging Face](https://huggingface.co/unsloth/Qwen3.6-35B-A3B)). Best for a deliberate sparse-model test on a larger workstation.

| Starting lane | Choose it for | Keep fixed during first test |
| --- | --- | --- |
| 27B dense Q3 | A 16 GB GPU planning target with fewer runtime variables | Exact GGUF pin, 4K-8K context, single request |
| 27B dense Q4 | A quality comparison with more memory headroom | Same prompt pack and server build |
| 35B-A3B MoE Q4 | A deliberate sparse-model test on a 24 GB+ workstation | Same context, sampling, and acceptance tests |
| Ollama Tag | The absolute shortest setup (rather than artifact control) | Explicit tag and observed context allocation |

## Decode the Quant Name

Unsloth's Dynamic 2.0 GGUFs use model-specific calibration data instead of applying a uniform quantization recipe everywhere. Treat the filename as your exact deployment label.

For a file like `Qwen3.6-35B-A3B-UD-Q4_K_M.gguf`, you are looking at the model family (Qwen3.6), parameter shape (35B-A3B), Unsloth Dynamic quant label (UD), bit width (Q4), and file format (GGUF).

Use this rule of thumb for bit-width before downloading ([Unsloth Qwen3.6 Guide](https://unsloth.ai/docs/models/qwen3.6)):

- **Q3:** Baseline for a 16 GB dense test (27B needs ~15 GB at 3-bit, 35B needs ~17 GB).
- **Q4:** The default useful local coding target (27B needs ~18 GB at 4-bit, 35B needs ~23 GB).
- **Q5/Q6:** Try when you have VRAM headroom.
- **Q8 or BF16:** For strict quality comparisons or server-class hardware.

*Note: The sizes above are baseline weight storage. Runtime memory will climb based on context length, concurrency, and buffers.*

## Run One Local Endpoint

`llama.cpp` is the core local inference engine. You can build it directly from source to maintain visibility over CUDA or Metal support ([llama.cpp GitHub](https://github.com/ggml-org/llama.cpp)).

On Linux with an NVIDIA GPU:

```bash
git clone https://github.com/ggml-org/llama.cpp
cmake -S llama.cpp -B llama.cpp/build -DGGML_CUDA=ON
cmake --build llama.cpp/build --config Release -j --target llama-server llama-cli

# Start the server with a 27B dense Q3 pin and short context
./llama.cpp/build/bin/llama-server \
  -hf unsloth/Qwen3.6-27B-GGUF:UD-Q3_K_XL \
  --alias local-qwen36 \
  --ctx-size 8192 \
  --n-gpu-layers 99 \
  --host 127.0.0.1 \
  --port 8080
```

*(If building without an NVIDIA GPU, omit `-DGGML_CUDA=ON` to rely on CPU, Apple Metal, or another backend).*

### Verify the Endpoint Contract

First launches spend time resolving and downloading the file from Hugging Face. Once running, verify that your API responds correctly before attaching a coding client.

```bash
curl -fsS http://127.0.0.1:8080/health

curl -fsS http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer local' \
  -d '{
    "model": "local-qwen36",
    "messages": [
      {"role": "user", "content": "Reply with exactly: endpoint-ready"}
    ],
    "temperature": 0,
    "max_tokens": 16,
    "stream": false
  }'
```

Qwen3.6 ships with "thinking" enabled by default. If your coding client misinterprets internal reasoning traces, disable it on the server using `--chat-template-kwargs '{"enable_thinking":false}'` ([Unsloth Qwen3.6 Guide](https://unsloth.ai/docs/models/qwen3.6)).

## Add MTP After the Plain Run Works

Multi-Token Prediction (MTP) allows a drafted path to propose several future tokens simultaneously, which the main model verifies in parallel to boost generation speed. This methodology is conceptually similar to Google's implementations for Gemma 4 ([Gemma 4 MTP Overview](https://ai.google.dev/gemma/docs/mtp/overview)).

Unsloth maintains dedicated `-MTP-GGUF` repositories for Qwen3.6. Once your plain run is stable, switch to the MTP GGUF file and add the flags `--spec-type draft-mtp --spec-draft-n-max 2` ([Unsloth Qwen3.6 MTP Repository](https://huggingface.co/unsloth/Qwen3.6-35B-A3B-MTP-GGUF)).

**Comparison Rules for MTP:**

- Only compare plain decoding against MTP decoding with the exact same base model, quant tier, context length, and hardware state.
- Unsloth reports roughly 1.4x to 2.2x faster inference, but you must independently verify that output formatting and JSON validity do not degrade under speculation.

## Scale Context and Add Vision

While Qwen3.6 officially supports up to 262,144 tokens of native context ([Qwen3.6 GitHub](https://github.com/QwenLM/Qwen3.6)), context dictates KV cache size and causes heavy memory pressure.

**Context Ladder:**

1. **4K-8K:** Smoke test and basic health check.
2. **16K-32K:** Standard local chat and file-level edits.
3. **64K-128K:** Agentic workspace tasks (requires ample VRAM).

**Vision Integration:**
Unsloth provides multimodal projector (`mmproj`) files for Qwen3.6. **Always prove text generation works first.** Only after text is verified should you add the matching `mmproj` file to your `llama-server` command.

### Common Failure Modes

- **Gibberish or Broken Output:** Unsloth tracks a known bug where CUDA 13.2 causes gibberish output with these GGUFs. Downgrade below 13.2 or upgrade to 13.3+ if you encounter this ([Unsloth Qwen3.6 Guide](https://unsloth.ai/docs/models/qwen3.6)). Alternatively, ensure your `llama.cpp` build is pulled from a recent commit.
- **Crash on First Prompt:** Your requested `--ctx-size` is likely too large for your KV cache budget. Drop back to 8192 and test again.
- **Tool JSON Malformed:** Lower the temperature and clearly stipulate the output schema in your system prompt.

## Tuning for Coding and Baselines

For rigorous coding generation, Unsloth recommends avoiding a greedy `temperature 0` in thinking mode to prevent repetition loops. Start with `temperature 0.6`, `top_p 0.95`, and `top_k 20` ([Unsloth Qwen3.6 Guide](https://unsloth.ai/docs/models/qwen3.6)).

Keep a fixed prompt pack to establish baselines. When evaluating Qwen3.6, compare it strictly against peer long-context coding models using the same tests. For instance, evaluate its 1M context potential against MIT-licensed competitors like GLM-5.2 ([GLM-5.2 Announcement](https://z.ai/blog/glm-5.2)) or DeepSeek V4 Flash 0731 ([DeepSeek-V4-Flash-0731 Hugging Face](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731)). While these specific large models may not fit on a single workstation, tracking their performance sets a clear quality bar for your local MoE setup.
