## 1. Introduction: The Local Footprint

- **Core Concept:** Running a local assistant ensures absolute code privacy and eliminates per-token API costs.
- **Current State:** Gemma 4 is Google's Apache 2.0 open-weights family featuring native system-prompt support, multimodal capabilities, and massive context windows (128K or 256K).
- **The Narrative Hook:** Finding a model that fits is harder than running it. June 2026 updates transformed the local sizing ladder by introducing a 12B middle lane, Quantization-Aware Training (QAT) checkpoints for tighter memory packing, and Multi-Token Prediction (MTP) for accelerated token generation.

## 2. The Model Ladder: Pick the Right Tag

Shape this section around memory headroom rather than raw benchmark scores. A smaller model running entirely in VRAM will generally outperform a larger model that spills to CPU.

- **E2B & E4B (128K context):** The default laptop endpoints. Start with `gemma4:e4b`. It acts as the standard baseline for 16 GB machines. Use `gemma4:e2b` only when memory is strictly limited.
- **12B Unified (256K context):** The newest middle lane. Move here if `gemma4:e4b` fits comfortably and you need higher reasoning quality, provided you still have headroom.
- **26B A4B (256K context):** The workstation MoE (Mixture of Experts) model. It contains 26B total parameters but activates only 4B per token, offering superior reasoning with less latency than a dense model, making it a strong fit for 24 GB+ GPUs.
- **31B Dense (256K context):** The heavy 20 GB baseline. Only use this for direct large-model comparisons, as it leaves very little room for context and cache on standard hardware.
- **Cloud Tags Warning:** Explicitly state that `gemma4:cloud` and `gemma4:31b-cloud` are hosted inference endpoints provided by Ollama, not local artifacts to download.

## 3. QAT vs. MTP: Solving Different Bottlenecks

Clarify that these two optimizations solve entirely different problems and should be applied systematically.

- **QAT (Quantization-Aware Training) for Memory:** Standard post-training quantization compresses a finished model, which can degrade logic. QAT models train under simulated low-precision constraints. Using a QAT tag drastically reduces the memory footprint (e.g., E2B drops from 7.2 GB to 4.3 GB; E4B drops from 9.6 GB to 6.1 GB). Try QAT tags (like `gemma4:e4b-it-qat`) if standard weights force the model into CPU offload.
- **MTP (Multi-Token Prediction) for Speed:** MTP addresses decode latency via speculative decoding. A small draft model predicts upcoming tokens, and the main model verifies them in a single pass. This improves tokens-per-second generation (often by 1.4x to 1.9x) but does *not* save memory; in fact, the draft head adds slightly to the VRAM footprint. Only implement MTP once you have secured a stable memory fit.

## 4. Memory Math: Context Windows and KV Cache

- **Core Concept:** The published size of a model is just the static weight artifact. At inference, the **KV cache** (Key-Value cache) consumes memory that scales dynamically with your context length. A model that runs smoothly at 4K context might crash or spill to CPU at 64K.
- **Tuning Context (`num_ctx`):** Ollama may default to a conservative context limit (often 4K or 32K depending on VRAM). For serious coding, override this to match the task by setting `OLLAMA_CONTEXT_LENGTH=32768 ollama serve` or passing `"num_ctx": 32768` in the API options payload.
- **Verification:** Run `ollama ps` mid-generation. If the `PROCESSOR` column shows partial CPU usage, the generation will drag. Fix this by lowering `num_ctx`, dropping to a QAT tag, or stepping down one model size.

## 5. API Integration and Modalities

- **Dual API Surfaces:** Use the OpenAI-compatible `/v1/chat/completions` endpoint for seamless SDK integrations. Use the native Ollama API (`/api/generate`) when you need exact parameter control, such as adjusting `num_ctx` or setting recommended Gemma 4 parameters (`temperature: 1.0`, `top_p: 0.95`).
- **Thinking Tokens:** Gemma 4 utilizes explicit thinking controls. Enable this by prepending `<|think|>` at the start of the system prompt.
- **Multimodal Scope:** Google recommends placing images before text and audio after text. However, local functionality depends entirely on Ollama's current tag support. Do not assume local audio processing works just because Google's model card allows it; verify the specific Ollama tag first.

## 6. The Practice Lab: Diagnosing Bottlenecks

- **Symptom Matrix:**

- *First token is slow:* Prompt length is too large or model is cold-loading.
- *Decode starts fast but degrades:* The KV cache expanded and pushed processing onto the CPU. Reduce `num_ctx`.
- *MTP doesn't improve prompt processing:* Expected behavior. MTP accelerates decode throughput (eval time), not prompt ingestion (time to first token).
- **Benchmarking Script:** Provide a `curl` example using `"stream": false` against the native API.
