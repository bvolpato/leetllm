**FP32** is a 32-bit floating-point number, usually the IEEE 754 binary32 format. Each value occupies four bytes and uses one sign bit, eight exponent bits, and 23 stored fraction bits. Normal numbers have an implicit leading significand bit, giving about seven decimal digits of precision. Its exponent range is much wider than FP16 and matches BF16's eight-bit exponent layout.

## Storage and arithmetic are separate decisions

A tensor's storage dtype determines how many bytes its values occupy in memory. An operation's compute or accumulation dtype determines how intermediate arithmetic behaves. A mixed-precision matrix multiplication can consume FP16 or BF16 inputs, accumulate products in FP32, and store its output in a narrower format. Keeping optimizer moments or master weights in FP32 can preserve small updates even when forward and backward tensors use fewer bits.

FP32 input and output tensors describe storage formats; GPU backends can use TF32 or other reduced-precision internal paths according to precision settings. [PyTorch's numerical-accuracy notes](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html) describe this distinction. Check the operation's precision policy when using an FP32 run as a numerical reference.

## Example

One billion FP32 parameters require four billion bytes, approximately 3.73 GiB, for weights alone. Storing their gradients in FP32 adds another four billion bytes. Adam's two FP32 moment tensors contribute eight billion more bytes. Together, those three inventory categories total 16 billion bytes before activations, temporary workspaces, communication buffers, or allocator overhead.

Switching only the stored weights to BF16 cuts that weight term from four bytes to two bytes per parameter. It doesn't automatically change the gradient, optimizer-state, or accumulation dtype. Inspect each tensor and operation independently instead of assuming one mixed-precision label describes the entire run.

## Why it matters here

Mixed-precision training, distributed sharding, quantization, and GPU sizing all use FP32 as a reference for numerical precision and memory cost. Explicitly separating storage, accumulation, and optimizer state prevents both unstable updates and misleading bytes-per-parameter estimates.
