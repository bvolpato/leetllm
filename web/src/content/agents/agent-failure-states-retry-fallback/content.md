A deployment agent asks the release controller to queue a rollback for `deploy-412` back to `rev-17`. Downstream, the controller writes job `job-1` into durable storage and transmits a confirmation, yet the TCP link drops before that response reaches the agent. From the caller's vantage point, only a silent timeout remains.

That single timeout branches into two dangerous overreactions when recovery code guesses instead of checking. Treating an unreadable socket as proof that "nothing ran" tempts the agent to generate a fresh operation and queue a duplicate rollback on top of `job-1`. Conversely, reporting "rollback succeeded" misleads operators into believing traffic shifted when, at most, a job may or may not have entered a queue.

Both mistakes stem from filling missing telemetry with an optimistic or pessimistic assumption. Reliable recovery preserves the uncertainty explicitly: first determine what remote state actually exists, and only then choose an action permitted in that state. While [agent memory](/learn/agent-memory-persistence-patterns) carries context across model turns, it cannot verify external truth or turn a non-repeatable mutation into a safe retry. The <span data-glossary="agent-runtime">agent runtime</span> around model calls and tools owns those guarantees deterministically, as shown in the local SQLite and async simulations below.

## Separate status inspection from write permission

Before the first packet hits the controller, trace what the user actually authorized. When an operator asks, *"What happened to deployment deploy-412?"*, a read-only status check fits inside that request, whereas triggering a rollback alters production and requires explicit separate authorization. A planned tool sequence generated by the language model cannot elevate a question into permission to mutate live infrastructure.

Every <span data-glossary="tool-calling">tool call</span> emitted by a model is strictly an untrusted proposal until validated in host code. Before dispatching, the runtime verifies the tool name, parameter schema, target resource identifier, and caller permission set against authenticated session state rather than trusting model text. Passing JSON schema validation alone confirms only syntax; it never confirms that a caller may touch a given service or alter a deployment revision.

In the runnable validation function below, authorized deployment identifiers represent an external permission lookup stored outside prompt history. Both mismatched tool names and unauthorized targets raise cleanly before execution begins, leaving only validated lookup payloads to reach the client layer. Notice how copying only checked fields strips away unexpected arguments before forwarding anything downstream.

```python title="validate-status-lookup.py"
import re

class RejectedProposal(Exception):
    pass

def validate_lookup(tool: str, args: dict, requested_deploy: str, allowed_deploys: set[str]) -> dict[str, str]:
    if tool != "get_deploy":
        raise RejectedProposal("only get_deploy is permitted for status queries")
    if set(args) != {"id"}:
        raise RejectedProposal("get_deploy requires exactly one key: id")
    deploy_id = args["id"]
    if not re.fullmatch(r"deploy-[0-9]{3,}", deploy_id):
        raise RejectedProposal("id must match deploy-<digits>")
    if deploy_id != requested_deploy or deploy_id not in allowed_deploys:
        raise RejectedProposal("target deployment is outside task permissions")
    return {"id": deploy_id}

test_proposals = [
    ("get_deploy", {"deploy_id": "deploy-412"}),
    ("create_release", {}),
    ("get_deploy", {"id": "deploy-413"}),
    ("get_deploy", {"id": "deploy-412"}),
]
for tool, args in test_proposals:
    try:
        print("accepted:", validate_lookup(tool, args, "deploy-412", {"deploy-412"}))
    except RejectedProposal as exc:
        print(f"rejected ({tool}): {exc}")
```

## Classify failures by execution stage

Dozens of underlying faults surface to users as *"the agent stopped working,"* yet each demands a different recovery response depending on where execution stopped. Pinpointing the exact failing interface separates safe deterministic fixes from blind repetition that multiplies damage. The three execution stages below establish what failed and what action keeps remote state intact:

1. **Proposal validation:** Missing fields, unknown tools, or schema errors fail synchronously inside host code prior to any network traffic. If the underlying intent stays within scope, return the structured validation diagnostic to the model and validate any updated output through the full host check.
2. **Transport and controller commit:** Network timeouts, resets, or `502`/`503` overload responses leave remote state ambiguous when mutating requests may already have landed. Reads retry under strict deadlines and backoff; writes reconcile remote state via a stable operation key before deciding whether to replay or halt.
3. **Result interpretation:** A downstream API can return HTTP `200` alongside an application-level failure payload or confirm *queued* status without finishing deployment. Parse explicit machine states carefully so `queued` never promotes into `completed` without confirmation from the execution worker.

| Observed symptom | Failing stage | Confirmed state | Safe next action |
|---|---|---|---|
| Missing argument or invalid type | Proposal check | Tool never invoked | Return structured diagnostic; revalidate retry |
| Permission denied | Policy gate | Action unauthorized | Halt execution; request explicit approval |
| Read timeout or `503` | Transport layer | State unread | Retry read with backoff, jitter, and deadline |
| Write timeout or dropped socket | Remote commit | Outcome unknown | Query operation key or replay unchanged idempotently |
| Controller confirms `queued` | Async queue | Enqueued, not finished | Subscribe to worker status or report `queued` only |

Keeping these stages independent prevents category errors during incident handling. For instance, treating a policy denial as a transient timeout causes hopeless retries, while treating an unconfirmed queued job as completed misleads downstream callers. Clear stage tagging inside structured trace logs accelerates post-incident debugging as well.

## Reconcile uncertain writes with stable keys

An <span data-glossary="idempotency">idempotent</span> endpoint produces the exact same persistent side effect whether executed once or retried five times after dropped responses. Achieving true idempotency requires server-side coordination: the client attaches a stable operation key representing *one logical action*, and the server atomically stores both the side effect and the key inside a single database transaction.[^awsIdempotentApis2026] Merely generating a fresh UUID per HTTP request accomplishes nothing, because each retry appears to the server as an unrelated brand-new command. Keeping those two identifiers distinct makes every retry safe to trace without duplicating downstream state:

| Identifier | Example value | Lifetime and ownership |
|---|---|---|
| Logical operation key | `rb-412-1` | Constant across all retries for one logical rollback |
| Transport trace ID | `att-9f2c` | Fresh per network attempt for log correlation |

In the local SQLite controller implementation below, the `jobs` and `operations` tables update inside a single `BEGIN IMMEDIATE` write transaction.[^sqliteTransactions2026] Injecting a fault before commit rolls both inserts back together cleanly, whereas dropping the reply after commit leaves both rows durable. Subsequent queries or unchanged retries using `rb-412-1` recover `job-1` deterministically without inserting duplicate jobs, while mutating `rev-17` to `rev-16` under the same key raises a `KeyConflict`. Watch how both sequential replay and multi-worker concurrency resolve cleanly against that single-writer lock.

<!-- leetllm: test, output=show -->

```python title="lost-reply-idempotency.py"
import json
import sqlite3
from concurrent.futures import ThreadPoolExecutor
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory
from threading import Barrier

class KeyConflict(Exception):
    pass

class Controller:
    """Durable SQLite job controller supporting atomic operation keys."""

    def __init__(self, db_path: Path):
        self.db_path = db_path
        with closing(sqlite3.connect(db_path)) as db, db:
            db.executescript("""
                CREATE TABLE IF NOT EXISTS jobs (
                    id INTEGER PRIMARY KEY,
                    payload TEXT NOT NULL,
                    state TEXT NOT NULL
                );
                CREATE TABLE IF NOT EXISTS operations (
                    op_key TEXT PRIMARY KEY,
                    payload TEXT NOT NULL,
                    job_id INTEGER NOT NULL REFERENCES jobs(id)
                );
            """)

    def enqueue(self, op_key: str, deploy_id: str, revision: str, fault: str | None = None) -> str:
        payload = json.dumps({"deploy_id": deploy_id, "revision": revision}, sort_keys=True)
        with closing(sqlite3.connect(self.db_path)) as db, db:
            db.execute("BEGIN IMMEDIATE")
            existing = db.execute(
                "SELECT payload, job_id FROM operations WHERE op_key = ?", (op_key,)
            ).fetchone()
            if existing:
                if existing[0] != payload:
                    raise KeyConflict("operation key already bound to different arguments")
                return f"job-{existing[1]}"
            job_id = db.execute(
                "INSERT INTO jobs(payload, state) VALUES (?, 'queued')", (payload,)
            ).lastrowid
            db.execute("INSERT INTO operations VALUES (?, ?, ?)", (op_key, payload, job_id))
            if fault == "before_commit":
                raise TimeoutError("link dropped before commit")
        if fault == "after_commit":
            raise TimeoutError("reply dropped after commit")
        return f"job-{job_id}"

    def lookup(self, op_key: str) -> tuple[str, str] | None:
        with closing(sqlite3.connect(self.db_path)) as db:
            row = db.execute(
                """
                SELECT jobs.id, jobs.state
                FROM operations
                JOIN jobs ON jobs.id = operations.job_id
                WHERE operations.op_key = ?
                """,
                (op_key,),
            ).fetchone()
            return None if row is None else (f"job-{row[0]}", row[1])

    def job_count(self) -> int:
        with closing(sqlite3.connect(self.db_path)) as db:
            return db.execute("SELECT COUNT(*) FROM jobs").fetchone()[0]

with TemporaryDirectory() as directory:
    controller = Controller(Path(directory) / "controller.sqlite")
    try:
        controller.enqueue("rb-412-1", "deploy-412", "rev-17", fault="after_commit")
    except TimeoutError:
        print("client saw: outcome unknown")

    # Reopen the database after simulated caller restart and reconcile via op_key.
    controller = Controller(Path(directory) / "controller.sqlite")
    print("reconciled:", controller.lookup("rb-412-1"))
    print("same-key replay:", controller.enqueue("rb-412-1", "deploy-412", "rev-17"))

    try:
        controller.enqueue("rb-412-1", "deploy-412", "rev-16")
    except KeyConflict as exc:
        print("rejected:", exc)

    try:
        controller.enqueue("rb-413-1", "deploy-413", "rev-17", fault="before_commit")
    except TimeoutError:
        pass
    assert controller.lookup("rb-413-1") is None
    print("queued jobs after rollback fault:", controller.job_count())

    start = Barrier(2)
    def competing_send(_: int) -> str:
        start.wait(timeout=5)
        return controller.enqueue("rb-414-1", "deploy-414", "rev-17")

    with ThreadPoolExecutor(max_workers=2) as pool:
        results = list(pool.map(competing_send, range(2)))
    print("concurrent race:", results, "| total jobs:", controller.job_count())
```

### Match replay behavior to exact server semantics

Every API defines its own rules for retention windows, error caching, and conflict detection, so never infer server guarantees from generic client wrappers. For instance, Stripe's v1 idempotency endpoint saves both successful bodies and server `500` responses for identical keys and prunes stored records after at least 24 hours, whereas parameter validation rejections before handler execution leave no saved result.[^stripe2026IdempotentRequests] Reusing a pruned key after expiration behaves like a brand-new charge, while replaying a cached `500` simply reproduces that saved error rather than creating a clean run. Reading endpoint semantics up front stops clients from inadvertently repeating bad keys or inventing duplicate workarounds.

When querying an eventually consistent endpoint returns *"not found,"* treat absence carefully because replica lag can hide a write that just committed on the primary node. Turning a stale read miss into permission to dispatch a brand-new mutation without idempotency keys creates split writes. Keep ambiguous entries in `unknown` state until primary reconciliation or manual triage resolves them.

Infrastructure operations also illustrate why compensation is a new forward action rather than a magical undo. Suppose an agent drains a Kubernetes node (`kubectl cordon` and eviction) to prepare maintenance, only to discover replacement capacity is exhausted; uncordoning the node restores future scheduling without teleporting evicted pods back to their original hosts.[^kubernetes2026DrainNode] Similarly, reversing a committed step inside a multi-service Saga does not have to run in strict reverse order when parallel compensations, forward repairs, or human approvals fit domain rules better, and any timeout during compensation creates one more ambiguous operation requiring tracking.[^azure2026CompensatingTransaction] Treating compensation as its own audited operation guarantees failures mid-rollback leave the same durable trace as forward execution.


## Restore workflow checkpoints and verify live state

A <span data-glossary="workflow-checkpoint">checkpoint</span> lets a long-running workflow survive pod restarts, yet restoring local progress never rewinds external systems. If a worker crashed right after saving *"about to submit rb-412-1,"* restarting from that frame while the remote controller already enqueued `job-1` will hit the same send path again unless operation keys and remote reconciliation bridge the crash window. Persist the chosen operation key *before* emitting I/O, then record external confirmations upon arrival.

Modern orchestration frameworks make this gap explicit in their execution models. LangGraph checkpointers serialize thread state at super-step intervals using SQLite or PostgreSQL storage so interrupted threads resume cleanly, while Temporal reconstructs state by replaying deterministic workflow histories and skipping already-recorded Activity completions.[^langgraph2026checkpointers][^temporal2026workflow] However, if an Activity completes its remote API call just milliseconds before crashing locally and fails to record completion, Temporal still schedules that Activity again on retry, making idempotency at the Activity destination mandatory.[^temporal_activity_definition] Because neither framework re-verifies whether an older human approval or live resource revision still holds after downtime, your executor must check live preconditions before mutating anything downstream.

## Retry reads with jittered backoff and hard deadlines

For idempotent read-only queries (`GET /runs/deploy-412`), transient overloads warrant retries, yet unbounded or uncoordinated retries accelerate outages. First agree on precise terminology: a budget of three attempts allows **one initial attempt plus at most two retries**, not three extra attempts after the first fault. Even with capped attempt counts, 500 failing workers waiting an identical deterministic `0.5` seconds hammer the controller simultaneously again half a second later.

Exponential backoff lengthens gaps as failures accumulate, while **full jitter** spreads clients uniformly across the delay window so retries desynchronize naturally, with zero-indexed failure counter $k \ge 0$, base delay $T_0$, and ceiling $T_{\max}$:[^awsbackoff]

$$
T_{\text{sleep}} = \operatorname{random}\left(0, \min\left(T_{\max}, T_0 \cdot 2^k\right)\right)
$$

When an upstream server responds with HTTP `429` or `503` and an explicit `Retry-After` header, honor that delay as a non-negotiable minimum floor, keeping in mind that `Retry-After` governs wait duration rather than granting permission to repeat non-idempotent writes.[^rfc9110RetryAfter] Notice the synchronization trap hidden inside `max(retry_after, jitter)`: whenever `retry_after` exceeds the local jitter cap (such as `5.0s` vs `0.2s`), `max` returns `5.0s` for every single client and aligns the entire fleet into another thundering herd. Adding bounded jitter *on top of* `retry_after` restores client dispersion while still satisfying the provider floor, provided the combined sleep still fits inside the caller's remaining deadline, as implemented below.

<!-- leetllm: test, output=show -->

```python title="bounded-read-retry.py"
import random
from dataclasses import dataclass

class TransientReadError(Exception):
    def __init__(self, message: str, retry_after: float = 0.0):
        super().__init__(message)
        if retry_after < 0:
            raise ValueError("retry_after must be nonnegative")
        self.retry_after = retry_after

class DeadlineExceeded(Exception):
    pass

@dataclass
class VirtualClock:
    now: float = 0.0
    waits: list[float] | None = None

    def __post_init__(self) -> None:
        self.waits = []

    def sleep(self, seconds: float) -> None:
        assert self.waits is not None
        self.waits.append(seconds)
        self.now += seconds

def retry_read(
    call,
    *,
    attempts: int = 3,
    timeout: float = 10.0,
    base: float = 0.2,
    cap: float = 2.0,
    clock: VirtualClock,
    rng: random.Random,
):
    if attempts < 1 or timeout <= 0:
        raise ValueError("attempts must be >= 1 and timeout must be > 0")
    deadline = clock.now + timeout
    ceiling = min(base, cap)

    for attempt in range(attempts):
        remaining = deadline - clock.now
        if remaining <= 0:
            raise DeadlineExceeded("caller deadline exhausted before call")
        try:
            result = call(remaining)
        except TransientReadError as exc:
            if attempt + 1 == attempts:
                raise
            delay = exc.retry_after + rng.uniform(0.0, ceiling)
            if delay >= deadline - clock.now:
                raise DeadlineExceeded("required wait exceeds remaining deadline") from exc
            clock.sleep(delay)
            ceiling = min(cap, ceiling * 2)
        else:
            if clock.now >= deadline:
                raise DeadlineExceeded("response arrived after caller deadline")
            return result

# Verify 1) floor + jitter spreads waits cleanly and stops within deadline.
clamped = [max(5.0, random.Random(c).uniform(0.0, 0.2)) for c in range(8)]
spread = [5.0 + random.Random(c).uniform(0.0, 0.2) for c in range(8)]
assert len(set(clamped)) == 1 and len(set(spread)) == 8

clock = VirtualClock()
remaining_trace: list[float] = []
def fetch_deploy_status(remaining: float) -> str:
    remaining_trace.append(round(remaining, 3))
    if len(remaining_trace) < 3:
        raise TransientReadError("controller overloaded", retry_after=0.25)
    return "deploy-412 failed unit-tests"

msg = retry_read(fetch_deploy_status, clock=clock, rng=random.Random(7))
print("result:", msg)
print("waits:", [round(w, 3) for w in clock.waits], "| remaining:", remaining_trace)

# A 20s Retry-After hint against a 3s budget fails immediately without sleeping.
short_clock = VirtualClock()
short_calls = [0]
def long_backoff_hint(_remaining: float) -> str:
    short_calls[0] += 1
    raise TransientReadError("rate limited", retry_after=20.0)

try:
    retry_read(long_backoff_hint, timeout=3.0, clock=short_clock, rng=random.Random(1))
except DeadlineExceeded as exc:
    print("aborted early:", exc, "| calls:", short_calls[0], "| sleeps:", len(short_clock.waits))
```

## Distinguish forward progress from blind repetition

Repeating a tool does not always signal a runaway loop. Querying `get_deploy("deploy-412")` three times in a row while receiving the exact same error string wastes budget, whereas scanning ten paginated build log chunks gathers fresh diagnostic lines on every step. Detecting real stalls requires checking task-specific evidence accumulation rather than blindly counting tool names or exact argument hashes.

In the progress monitor below, trusted tool adapters extract distinct, task-verified evidence tokens (such as unseen log page IDs or newly resolved job state transitions). Repeated unchanged observations increment the `stalls` counter while new verified tokens reset `stalls` to zero, yet an independent `max_calls` limit still bounds runs that stream infinite novel pages without reaching closure. Notice that prompt timestamps or paraphrased model summaries are stripped out before comparison so cosmetic rewordings cannot masquerade as new evidence.

<!-- leetllm: test, output=show -->

```python title="progress-not-tool-count.py"
class StopRun(Exception):
    pass

class ProgressBudget:
    def __init__(self, max_calls: int = 8, max_stalls: int = 2):
        if max_calls <= 0 or max_stalls <= 0:
            raise ValueError("call and stall caps must be positive")
        self.max_calls, self.max_stalls = max_calls, max_stalls
        self.calls = 0
        self.stalls = 0
        self.seen: set[str] = set()

    def reserve_call(self) -> None:
        if self.calls >= self.max_calls or self.stalls >= self.max_stalls:
            raise StopRun("call cap or no-progress limit reached")
        self.calls += 1

    def record_evidence(self, tokens: set[str]) -> None:
        novel = tokens - self.seen
        self.stalls = 0 if novel else self.stalls + 1
        self.seen.update(tokens)

budget = ProgressBudget()
for batch in [{"status-v1"}, {"status-v1"}, {"log-page-1"}, {"log-page-1"}, {"log-page-1"}]:
    budget.reserve_call()
    budget.record_evidence(batch)

try:
    budget.reserve_call()
except StopRun as exc:
    print(f"stopped cleanly after {budget.calls} calls ({budget.stalls} stalls): {exc}")
```

### Track context length and cumulative spend separately

One common accounting confusion equates trimming prompt length with saving cumulative spend. Context capacity bounds **a single forward pass**, whereas token or dollar budgets measure **total tokens billed across every turn** in the session. Summarizing history shrinks *future* prompt inputs, yet it never refunds the tokens burned in prior turns.

Suppose every request sends a fixed $h$-token system prompt and each completed turn adds $s$ history tokens that stay in context across $n$ turns, making cumulative input tokens scale quadratically across requests:

$$
\text{Total Input} = n \cdot h + s \cdot \frac{n(n - 1)}{2}
$$

With $h = 100$, $s = 50$, and $n = 4$, individual prompts carry `100`, `150`, `200`, and `250` tokens, summing to `700` cumulative input tokens before adding generated outputs or cache multipliers. Enforce pre-flight budget reservations *before* issuing each request by adding worst-case prompt size plus `max_output_tokens`; if only 150 tokens remain in budget and the next request requires 120 input plus 80 output tokens, reject dispatch upfront instead of catching overrun errors afterward. When dispatching parallel tool-producing subcalls, allocate reservations atomically from a single shared budget ledger and hold unresolved timeout reservations until provider billing reconciles.

```checkpoint
An agent compresses its conversation window from 8,000 tokens down to 2,000 tokens via summarization. Did it recover 6,000 tokens of its cumulative run budget?
---
No. Compressing the prompt reduces input tokens for upcoming requests only; prior model passes have already been consumed and billed. Track per-call context limits and cumulative run budgets independently.
```

## Protect dependencies with generation-scoped circuit breakers

Per-run budgets protect a single trajectory, yet across hundreds of user sessions, blind retries still pound an unavailable service. A <span data-glossary="circuit-breaker">circuit breaker</span> halts repeated calls to an unhealthy dependency so downstream systems recover without absorbing constant probe storms.[^azure2026CircuitBreaker] Instead of wasting caller deadlines on dead sockets, the breaker intercepts calls immediately in host code.

Three explicit states govern behavior: **closed** passes normal traffic, **open** fails fast for a cooldown interval once counted dependency errors hit threshold, and **half-open** lets exactly one single probe through after cooldown ends to verify health. A successful probe returns to **closed**, whereas a dependency fault or canceled probe returns immediately to **open**. Crucially, application validation exceptions like `ValueError` propagate cleanly to callers and release the probe slot without marking the transport broken.

Concurrency introduces a subtle correctness bug when completions overlap across state changes. Suppose Call A begins under **closed** generation 4, stalls slowly, and meanwhile Call B times out and opens generation 5; when Call A finally finishes seconds later with `"ok"`, that stale success still belongs to Call A, yet letting it reset generation 5 back to **closed** would unmask a live outage immediately. Tagging every admitted call with the breaker's current `generation` integer guarantees stale completions return cleanly to their own caller while never mutating a newer breaker generation. Cancellation during a half-open probe similarly requires explicit `probe = False` cleanup inside `finally`/exception blocks so canceled tasks never strand the breaker permanently unable to probe again.

<!-- leetllm: test, output=show -->

```python title="circuit-breaker-faults.py"
import asyncio

class CircuitOpen(Exception):
    pass

class CircuitBreaker:
    def __init__(self, threshold: int = 2, cooldown: float = 5.0, clock=lambda: 0.0):
        if threshold <= 0 or cooldown <= 0:
            raise ValueError("threshold and cooldown must be positive")
        self.threshold, self.cooldown, self.clock = threshold, cooldown, clock
        self.state = "closed"
        self.failures = 0
        self.generation = 0
        self.opened_at = 0.0
        self.probe_in_flight = False
        self.lock = asyncio.Lock()

    def _trip_open(self) -> None:
        self.state = "open"
        self.opened_at = self.clock()
        self.probe_in_flight = False
        self.generation += 1

    async def call(self, fn):
        async with self.lock:
            if self.state == "open":
                if self.clock() - self.opened_at < self.cooldown:
                    raise CircuitOpen("cooldown active")
                self.state = "half_open"
            if self.state == "half_open" and self.probe_in_flight:
                raise CircuitOpen("half-open probe already running")
            is_probe = self.state == "half_open"
            if is_probe:
                self.probe_in_flight = True
            call_gen = self.generation

        try:
            result = await fn()
        except BaseException as exc:
            async with self.lock:
                if call_gen == self.generation:
                    if is_probe:
                        self.probe_in_flight = False
                    if isinstance(exc, (TimeoutError, ConnectionError)):
                        self.failures += 1
                        if is_probe or self.failures >= self.threshold:
                            self._trip_open()
                    elif is_probe and isinstance(exc, asyncio.CancelledError):
                        self._trip_open()
            raise

        async with self.lock:
            if call_gen == self.generation:
                self.state, self.failures, self.probe_in_flight = "closed", 0, False
        return result

async def exercise_breaker() -> None:
    now = [0.0]
    breaker = CircuitBreaker(threshold=1, cooldown=5.0, clock=lambda: now[0])
    started, release = asyncio.Event(), asyncio.Event()

    async def slow_ok() -> str:
        started.set()
        await release.wait()
        return "gen-0 result"

    async def down_err() -> str:
        raise TimeoutError("controller unreachable")

    stale_task = asyncio.create_task(breaker.call(slow_ok))
    await started.wait()
    try:
        await breaker.call(down_err)
    except TimeoutError:
        pass
    release.set()
    assert await stale_task == "gen-0 result" and breaker.state == "open"
    print("late completion leaves state:", breaker.state)

    now[0] = 5.0
    started.clear()
    release.clear()
    probe = asyncio.create_task(breaker.call(slow_ok))
    await started.wait()
    try:
        await breaker.call(down_err)
    except CircuitOpen:
        print("concurrent second probe: rejected")

    probe.cancel()
    try:
        await probe
    except asyncio.CancelledError:
        pass
    assert breaker.state == "open" and not breaker.probe_in_flight

    now[0] = 10.0
    release.set()
    assert await breaker.call(slow_ok) == "gen-0 result"
    print("post-cancel recovery probe:", breaker.state)

    try:
        await breaker.call(down_err)
    except TimeoutError:
        pass
    now[0] = 15.0
    async def schema_mismatch() -> str:
        raise ValueError("malformed payload from caller")
    try:
        await breaker.call(schema_mismatch)
    except ValueError:
        pass
    assert breaker.state == "half_open" and not breaker.probe_in_flight
    assert await breaker.call(slow_ok) == "gen-0 result"
    print("non-health exception probe:", breaker.state)

asyncio.run(exercise_breaker())
```

## Build tiered fallbacks with honest evidence claims

When a primary model or downstream controller stays unavailable after retries and breaker checks, silent fallback chains prevent total stalls only when capability degradation remains strictly truthful. Swapping inference providers or models cannot invent live production observations that the caller never received. Every fallback tier preserves caller permissions, remaining deadline, and cancellation signals while narrowing what the system claims to know:

- **Backup model provider:** Normalize message roles, tool schemas, context windows, and refusal formats carefully across providers, verify data residency approvals before forwarding user inputs, and validate outputs with the exact same deterministic host rules.
- **Narrowed read-only or classification mode:** Fall back to a smaller model or deterministic summarizer over already-fetched logs while disabling mutation tools altogether, matching capability strictly to verified evaluation behavior.
- **Freshness-gated cache or structured handoff:** Serve timestamped cached snapshots only inside strict age windows, or pause automation cleanly and generate a redacted handoff bundle when present state cannot be established.

The deterministic formatter below demonstrates why freshness rules belong in host logic rather than inside generated model text. An observation confirming `queued` 10 seconds ago within a 30-second window can responsibly answer *"job-1 was queued when checked 10s ago,"* whereas a 900-second-old `completed` cache entry or unmatched record yields only *"Current rollback status is unavailable."* Accepting a self-reported `is_fresh=True` boolean from model output would let a backup model hallucinate present certainty out of stale memory.

## Report recovery outcomes without hiding unresolved load

Evaluating reliability starts by refusing to collapse partial or escalated outcomes into binary "success." Suppose 100 failed agent runs enter recovery: 60 finish the intended task after idempotent reconciliation, 12 return an explicitly dated degraded answer, 18 route safely to human handoff, and 10 stall unresolved. Reporting `90% success` conceals both a 12% drop in capability and 18 human tickets added to engineering queues, hiding operational strain behind an inflated metric.

| Recovery outcome | Count (of 100) | Operational meaning |
|---|---:|---|
| Full task completed | 60 | Downstream verifier confirms intended result |
| Degraded dated answer | 12 | Scoped fallback answer without full repair |
| Safe human handoff | 18 | Automation halted cleanly; reviewer work pending |

Track unique runs in the denominator rather than attempt counts, expose unresolved work explicitly, and emit trace-level observability on deduplicated replays, ambiguity durations, stall triggers, and circuit-open drops. Before trusting recovery logic in production, exercise every failure mode systematically through fault injection inside test harnesses held strictly outside agent prompts and memory, checking every transition listed below:

## Diagnose which stage failed first

On the surface, every failure looks like *"the agent could not finish."* Under the hood, three distinct stages fail for completely different reasons, and treating an authorization denial like a dropped socket guarantees worse fallout. Pinning down where execution broke directs your recovery logic toward an exact fix rather than blind repetition. Inspect the stage boundaries below to select the safest response in each situation:

1. **Proposal check before dispatch:** Missing arguments, unknown tool names, or unauthorized targets fail inside host validation before hitting the wire. If the task still allows it, return the exact error to the model and pass any revised call through the same permission check.
2. **Transport and remote commit:** Timeouts, connection resets, and `502`/`503` overload errors leave writes uncertain because the server may have committed right before the socket closed. Read calls can safely retry under a hard deadline, while mutating writes must look up or replay a stable operation key before doing anything else.
3. **Interpreting partial results:** Receiving HTTP `200` alongside `state="queued"` only establishes queue placement, never finished deployment. Wait for downstream execution updates or report the exact observed queue status honestly.

## Give every write one stable operation key

An operation is *idempotent* when repeating it yields the exact same intended outcome as executing it once. Attaching a random header to an ordinary endpoint buys nothing unless the server recognizes repeated keys, verifies matching arguments, and binds key registration to its persistent write inside a single transaction.[^awsIdempotentApis2026] A client that mints a brand-new UUID on each HTTP retry accidentally tricks the server into running duplicate work. Always pair one logical action with one stable client key while rotating only per-attempt trace tags.

Notice why a single `BEGIN IMMEDIATE` transaction inside SQLite closes both dropped-reply and concurrency races below.[^sqliteTransactions2026] Checking for `op_key` inside the same write lock as inserting `jobs` ensures that two workers dispatching `rb-414-1` simultaneously never queue duplicate jobs. Meanwhile, any simulated fault before commit leaves zero stray records behind while post-commit faults stay discoverable under lookup. Watch how lookup and replay both preserve a single database record regardless of timing.

```python title="recovery-lost-reply.py"
import json
import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory

class KeyConflict(Exception):
    pass

class Controller:
    def __init__(self, db_path: Path):
        self.db_path = db_path
        with closing(sqlite3.connect(db_path)) as db, db:
            db.executescript("""
                CREATE TABLE IF NOT EXISTS jobs (
                    id INTEGER PRIMARY KEY,
                    payload TEXT NOT NULL,
                    state TEXT NOT NULL
                );
                CREATE TABLE IF NOT EXISTS operations (
                    op_key TEXT PRIMARY KEY,
                    payload TEXT NOT NULL,
                    job_id INTEGER NOT NULL REFERENCES jobs(id)
                );
            """)

    def enqueue(self, op_key: str, deploy_id: str, revision: str, fault: str | None = None) -> str:
        payload = json.dumps({"deploy_id": deploy_id, "revision": revision}, sort_keys=True)
        with closing(sqlite3.connect(self.db_path)) as db, db:
            db.execute("BEGIN IMMEDIATE")
            existing = db.execute(
                "SELECT payload, job_id FROM operations WHERE op_key = ?", (op_key,)
            ).fetchone()
            if existing:
                if existing[0] != payload:
                    raise KeyConflict("same operation key cannot reuse changed arguments")
                return f"job-{existing[1]}"
            job_id = db.execute(
                "INSERT INTO jobs(payload, state) VALUES (?, 'queued')", (payload,)
            ).lastrowid
            db.execute("INSERT INTO operations VALUES (?, ?, ?)", (op_key, payload, job_id))
            if fault == "before_commit":
                raise TimeoutError("connection dropped before commit")
        if fault == "after_commit":
            raise TimeoutError("confirmation lost after commit")
        return f"job-{job_id}"

    def lookup(self, op_key: str) -> tuple[str, str] | None:
        with closing(sqlite3.connect(self.db_path)) as db:
            row = db.execute(
                "SELECT jobs.id, jobs.state FROM operations JOIN jobs ON jobs.id = operations.job_id WHERE op_key = ?",
                (op_key,),
            ).fetchone()
            return None if row is None else (f"job-{row[0]}", row[1])

with TemporaryDirectory() as directory:
    ctrl = Controller(Path(directory) / "ctrl.sqlite")
    try:
        ctrl.enqueue("rb-412-1", "deploy-412", "rev-17", fault="after_commit")
    except TimeoutError:
        print("Caller saw timeout")

    print("Lookup:", ctrl.lookup("rb-412-1"))
    print("Same-key replay:", ctrl.enqueue("rb-412-1", "deploy-412", "rev-17"))

    try:
        ctrl.enqueue("rb-412-1", "deploy-412", "rev-16")
    except KeyConflict as exc:
        print("Changed payload blocked:", exc)

    try:
        ctrl.enqueue("rb-413-1", "deploy-413", "rev-17", fault="before_commit")
    except TimeoutError:
        pass
    print("Uncommitted key exists?:", ctrl.lookup("rb-413-1") is not None)
```

## Retry reads with jitter and one hard deadline

For safe read-only lookups, waiting a fixed interval aligns every failing client into synchronized load spikes. Pairing exponential backoff with full jitter samples delays uniformly across the current window so concurrent clients fan out cleanly over time, bounded by ceiling $T_{\max}$ and base delay $T_0$ on retry $k$:[^awsbackoff]

$$
T_{\text{sleep}} = U\left(0, \min\left(T_{\max}, T_0 \cdot 2^k\right)\right)
$$

When a service sends a `Retry-After` duration or timestamp, treat it as a mandatory floor and sample jitter *above* that floor rather than wrapping `max(hint, jitter)`.[^rfc9110RetryAfter] Whenever `retry_after` exceeds your jitter ceiling, `max` forces every worker onto one identical wake-up second and recreates the very thundering herd backoff tried to prevent. Adding jitter after the hint restores client dispersion while respecting the pause, and checking the combined sleep against remaining caller deadline stops before overshooting timeout bounds. That single combined check runs cleanly in the deadline-aware wrapper below.

```python title="recovery-retry.py"
import random
from dataclasses import dataclass

class TransientReadError(Exception):
    def __init__(self, message: str, retry_after: float = 0.0):
        super().__init__(message)
        self.retry_after = retry_after

class DeadlineExceeded(Exception):
    pass

@dataclass
class SimClock:
    now: float = 0.0
    waits: list[float] | None = None

    def __post_init__(self) -> None:
        self.waits = []

    def sleep(self, seconds: float) -> None:
        assert self.waits is not None
        self.waits.append(seconds)
        self.now += seconds

def retry_read(call, *, attempts: int = 3, timeout: float = 10.0, base: float = 0.2, cap: float = 2.0, clock: SimClock, rng: random.Random):
    deadline = clock.now + timeout
    ceiling = min(base, cap)
    for attempt in range(attempts):
        remaining = deadline - clock.now
        if remaining <= 0:
            raise DeadlineExceeded("deadline exhausted")
        try:
            res = call(remaining)
        except TransientReadError as exc:
            if attempt + 1 == attempts:
                raise
            delay = exc.retry_after + rng.uniform(0.0, ceiling)
            if delay >= deadline - clock.now:
                raise DeadlineExceeded("wait exceeds remaining deadline") from exc
            clock.sleep(delay)
            ceiling = min(cap, ceiling * 2)
        else:
            if clock.now >= deadline:
                raise DeadlineExceeded("reply arrived past deadline")
            return res

clock = SimClock()
calls = 0
def flaky_status(rem: float) -> str:
    global calls
    calls += 1
    if calls < 3:
        raise TransientReadError("busy", retry_after=0.25)
    return f"ok with {rem:.2f}s left"

print(retry_read(flaky_status, clock=clock, rng=random.Random(7)))
print("waits:", [round(w, 3) for w in clock.waits])

# Long Retry-After hint exceeds the 3s budget, stopping with zero sleeps.
short_clock = SimClock()
def long_wait(_rem: float) -> str:
    raise TransientReadError("overloaded", retry_after=20.0)

try:
    retry_read(long_wait, timeout=3.0, clock=short_clock, rng=random.Random(1))
except DeadlineExceeded as exc:
    print("aborted:", exc, "| sleeps:", len(short_clock.waits))
```

Polling `get_deploy` for identical status JSON wastes turns, whereas fetching successive paginated log chunks collects genuinely new evidence on every call. ## Stop hammering down dependencies with circuit breakers

When downstream health stays broken across requests, retries only consume deadlines and delay recovery. A *circuit breaker* passes calls while **closed**, trips **open** to fail fast across a cooldown period once dependency failures breach threshold, and checks recovery with a single **half-open** probe afterward.[^azure2026CircuitBreaker] By failing immediately during an outage, callers recover budget cleanly and let struggling backends shed load. Adding a monotonically increasing generation tag then prevents slow completions from closing a newer open state.

Two subtle concurrency details separate reliable breakers from fragile prototypes. First, tracking an integer `generation` prevents an old in-flight response started under generation 0 from clearing an **open** state later tripped by generation 1. Second, cleaning up probe slots when tasks cancel ensures interrupted probes never lock every future check indefinitely.

<!-- leetllm: test, output=show -->

```python title="recovery-breaker.py"
import asyncio

class CircuitOpen(Exception):
    pass

class CircuitBreaker:
    def __init__(self, threshold: int = 1, cooldown: float = 5.0, clock=lambda: 0.0):
        self.threshold, self.cooldown, self.clock = threshold, cooldown, clock
        self.state, self.failures, self.generation = "closed", 0, 0
        self.opened_at = 0.0
        self.probe_busy = False
        self.lock = asyncio.Lock()

    def _open(self) -> None:
        self.state = "open"
        self.opened_at = self.clock()
        self.probe_busy = False
        self.generation += 1

    async def call(self, fn):
        async with self.lock:
            if self.state == "open":
                if self.clock() - self.opened_at < self.cooldown:
                    raise CircuitOpen("cooldown active")
                self.state = "half_open"
            if self.state == "half_open" and self.probe_busy:
                raise CircuitOpen("probe already in flight")
            is_probe = self.state == "half_open"
            if is_probe:
                self.probe_busy = True
            gen = self.generation

        try:
            res = await fn()
        except BaseException as exc:
            async with self.lock:
                if gen == self.generation:
                    if is_probe:
                        self.probe_busy = False
                    if isinstance(exc, (TimeoutError, ConnectionError)):
                        self.failures += 1
                        if is_probe or self.failures >= self.threshold:
                            self._open()
                    elif is_probe and isinstance(exc, asyncio.CancelledError):
                        self._open()
            raise

        async with self.lock:
            if gen == self.generation:
                self.state, self.failures, self.probe_busy = "closed", 0, False
        return res

async def demo() -> None:
    now = [0.0]
    breaker = CircuitBreaker(threshold=1, cooldown=5.0, clock=lambda: now[0])
    started, release = asyncio.Event(), asyncio.Event()

    async def slow() -> str:
        started.set()
        await release.wait()
        return "old result"

    async def unavailable() -> str:
        raise TimeoutError("dependency down")

    old = asyncio.create_task(breaker.call(slow))
    await started.wait()
    try:
        await breaker.call(unavailable)
    except TimeoutError:
        pass
    release.set()
    assert await old == "old result" and breaker.state == "open"
    print("Late success leaves:", breaker.state)

    now[0] = 5.0
    started.clear()
    release.clear()
    probe = asyncio.create_task(breaker.call(slow))
    await started.wait()
    probe.cancel()
    try:
        await probe
    except asyncio.CancelledError:
        pass
    assert breaker.state == "open" and not breaker.probe_busy

    now[0] = 10.0
    release.set()
    assert await breaker.call(slow) == "old result"
    print("After new probe:", breaker.state)

asyncio.run(demo())
```

## Make smaller claims when live data disappears

Switching to a backup model provider only swaps inference hosts; it never creates controller telemetry, enlarges permissions, or refreshes caller deadlines. Enforce freshness limits strictly in host code so cached telemetry reads carry explicit timestamps when valid and decline present-tense certainty whenever data grows stale or disappears. Never trust a backup model's self-reported assertion that cached text reflects live cluster state.

## Verify every fault path systematically

Testing recovery logic requires deterministic fault injection stored completely outside model context inside your evaluation harness. Keeping failure injectors independent of prompt memory guarantees tests evaluate actual runtime code paths rather than agent compliance hints. Verify every condition in the checklist below directly against real persistence and async locks before deploying:

| Injected fault | Expected observed outcome |
|---|---|
| Failure before SQLite commit | Zero persisted operations or queued jobs |
| Dropped confirmation after commit + replay | Same `job-1` returned with zero extra jobs |
| Reused key paired with altered revision | `KeyConflict` error, zero second job |
| `Retry-After` longer than remaining timeout | Immediate stop with zero sleeps |
| Novel log chunks from same paginated tool | Stall budget resets while hard call cap stays intact |
| Slow old completion after breaker trips open | Caller receives response; breaker remains open |
| Canceled half-open probe | Cancellation propagates; probe slot clears cleanly |
| Stale `completed` cache entry during outage | Refuses present completion claim cleanly |
