# Agent Failure & Recovery: manual source notes

Checked September 22, 2026. These notes replace the generated August outline. They support this lesson's specific mechanisms rather than prescribing a reusable article template.

- [AWS idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) distinguishes caller-scoped request identity, atomic token/effect recording, parameter mismatch, and late requests. A random key alone cannot make an arbitrary destination repeat-safe. Persist identity before the first dispatch and respect the destination's scope and retention contract.
- [Stripe API v1 idempotent requests](https://docs.stripe.com/api/idempotent_requests) retains executed request status/body, including 500s, compares parameters, and permits pruning after at least 24 hours. Validation failures and concurrent execution conflicts don't save a result. Don't universalize Stripe's contract or treat a retained error as permission to create another logical operation.
- [AWS backoff and jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) demonstrates load reduction in an optimistic-concurrency simulation. Full jitter reduces alignment, not all collisions or overload. The lesson's shared-floor counterexample is a separate deterministic calculation, not an AWS benchmark or live fleet measurement.
- [HTTP Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3) supports an HTTP date or nonnegative integer delay seconds. Our adapter converts a valid hint into a delay; the example treats it as a minimum and adds jitter. A hint doesn't establish idempotency or extend the caller's deadline.
- [Instructor retrying](https://python.useinstructor.com/concepts/retrying/) separates SDK transport sends from extraction attempts. Current integer validation retries don't automatically restart exhausted transport errors. Elapsed-time stopping doesn't interrupt an in-flight request, and token retry budgets aren't hard cumulative spend caps. Inspect the installed library and SDK versions; don't infer actual sends from configured limits.
- [OpenAI's historical reproducibility example](https://developers.openai.com/cookbook/examples/reproducible_outputs_with_the_seed_parameter) describes best-effort determinism. Temperature zero isn't a guarantee of identical hosted output. This isn't a recommendation that every current model supports seed or temperature parameters.
- [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) persist snapshots at super-step boundaries and pending task writes for successful nodes in a failed step. This isn't an arbitrary instruction-pointer snapshot or a transaction with an external controller. Persistent storage is required for restart recovery.
- [Temporal Workflow Execution](https://docs.temporal.io/workflow-execution) explains deterministic reconstruction from event history. Model requests and external I/O belong in Activities, with results recorded rather than model inference repeated as ordinary replayed workflow code.
- [Temporal Activity definitions](https://docs.temporal.io/activity-definition) explains that completed, recorded Activities aren't rerun during replay. A worker can commit an effect and fail before reporting completion, causing another execution. Destination repeat safety remains necessary; framework completion semantics don't certify exactly one external effect.
- [Microsoft circuit breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker) describes closed/open/half-open states, scoped failure classification, probes, and resource differentiation. A threshold crossing isn't proof a whole provider is down. The lesson's single-event-loop, generation-aware breaker is a local implementation with explicit neutral-error and cancellation policies.
- [Microsoft compensating transactions](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) explains concurrent work, application-specific recovery, optional forward repair, non-reverse ordering, parallel compensation, and manual intervention. Compensations can fail and need progress recording and repeat safety; not every destination supports a key-based API.
- [Kubernetes node maintenance](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/) states that uncordon permits scheduling new pods onto the node. It doesn't restore prior pod placement or prove the node healthy. The maintenance scenario is illustrative and executes no cluster commands.
- [Reflexion](https://arxiv.org/html/2303.11366) stores verbal task feedback for later trials without updating model weights. Reflection quality and feedback reliability still matter; a self-written lesson doesn't establish authority or external completion.

Teaching choices: preserve the lost-reply incident and real local SQLite transaction, contrast changed proposals with unchanged transport retries, ask readers to predict the floor/jitter calculation, and fault-test stale breaker completions, cancellation, and neutral errors. Keep context capacity separate from cumulative usage. Fallback routes require actual task evaluation, permitted data transfer, shared remaining budgets, and evidence adequate to the final claim; model size alone doesn't supply those properties.

Evidence limits: the executable fixtures make no model/provider calls, deployments, or Kubernetes mutations. Injected exceptions and fake clocks test local branches, not partitions, power loss, durable fleet coordination, or production cancellation. Source passages relevant to these claims were reviewed, not entire manuals or papers. No measured recovery, safety, latency, or model-superiority results are asserted.
