# Manual source notes: low-precision GPU programming

Reviewed September 22, 2026. Full 559-line original article, two marked examples, nine questions, eleven original reference records, native illustration, banner source/text, and generated research read directly. These notes support the individual lesson rather than prescribe a writing template.

- Element width isn't a universal throughput multiplier. TF32 still uses FP32 operand storage, and scales/padding/output/conversion affect bytes and performance. [PyTorch numerical accuracy](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html).
- OFP8 defines encodings and conversions, not arithmetic or scale selection. It requires support for RNE and both saturating/non-saturating modes, permits additional modes, and applies rounding before the overflow decision. E5M2's wider range doesn't preserve an unscaled 1e-7. [OFP8 specification](https://www.opencompute.org/documents/ocp-8-bit-floating-point-specification-ofp8-revision-1-0-2023-12-01-pdf-1).
- NVFP4 uses E2M1 elements, 16-element E4M3 block scales, and an FP32 global scale. MXFP4's block is 32 elements with E8M0. Transformer Engine's NVFP4 recipe separately supports 2D weight scaling and gradient stochastic rounding. Neither specifies the attention KV-cache dtype. [NVFP4 recipe](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/nvfp4/nvfp4.html).
- S means reconstruction scale in this lesson; alpha=1/S encodes. Use S=amax/format_max, not its reciprocal. Quantized-operand equations approximate the original operation; scale factoring in real arithmetic doesn't promise bitwise finite-precision equivalence. K-dependent block scales stay inside the sum.
- E8M0 codes 0 through 254 represent positive powers of two; 255 is NaN. The MX specification leaves dot-product internal precision/order implementation-defined and describes a scale-selection algorithm different from conservative upward rounding. [MX specification](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf).
- Current scaling's two reads occur during quantization. Delayed scaling records current amax while casting with historical scales; history and distributed reductions remain. The original chapter wrongly described GEMM/TMA as doing all this without reductions. [Current scaling](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/fp8_current_scaling/fp8_current_scaling.html), [delayed scaling](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/fp8_delayed_scaling/fp8_delayed_scaling.html).
- DeepSeek-V3 reports online 1x128/128x128 scales, partial-result FP32 promotions, and a separate quantization read/write path. Fused FP8 cast with TMA is a proposed improvement. The pinned DeepGEMM README likewise delegates casting/transposition to the caller. [Report](https://arxiv.org/html/2412.19437v2), [pinned README](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb6994a58b8a15b4b93bf13ccc16edf247/README.md).
- FP32 isn't the universally enforced accumulator type. Declared storage type doesn't guarantee every internal accumulation step. FTZ must name a device/instruction, and RNE absorption is rounding the updated weight, not necessarily rounding its separately represented update to zero. Stochastic rounding uses adjacent float values, not integer floor/ceiling; clipping breaks unbiasedness. [PTX](https://docs.nvidia.com/cuda/parallel-thread-execution/), [PyTorch precision controls](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html).
- The existing CPU cast of finite 500 produces 448 in the recorded 2.14 build, contradicting the article's comment promising NaN. Explicit CUDA __NV_NOSAT and __NV_SATFINITE have their own documented policies. CPU casts don't test GPU MMA. [CUDA FP8 conversions](https://docs.nvidia.com/cuda/cuda-math-api/cuda_math_api/group__CUDA__MATH__FP8__MISC.html).
- The two-row MX-style example reconstructs operands then uses CPU FP32 matmul, with FP32 scales. It doesn't pack E8M0 or satisfy Transformer Engine's shape eligibility. The 500 spike becomes 512 despite an exactly matching projected result. Tensor-wide errors include both operand quantizations. Four scale bytes are 6.25% overhead on 64 FP8 code bytes, not 0%. [MXFP8 recipe](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/mxfp8/mxfp8.html).
- PyTorch 2.14 matmul defaults differ from convolution. Prefer fp32_precision controls and don't mix old/new APIs. ROCm 10.0.0 distinguishes host/type, scalar compute, matrix-core, and library support; CDNA3 FNUZ differs from CDNA4/RDNA4 OCP encodings. [CUDA semantics](https://docs.pytorch.org/docs/2.14/notes/cuda.html), [ROCm matrix](https://rocm.docs.amd.com/en/docs-10.0.0/reference/precision-support.html).
